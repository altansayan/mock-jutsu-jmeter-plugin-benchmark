In the burn-in test, Fast Types (1000T) and Heavy Types (200T) wrote to the same JTL file. In the second half, only heavy types remained — so p95 appears higher and TPS appears lower. This is the expected effect of test design, not performance degradation.

Question 2
How is performance affected under 1000 concurrent calls? (real concurrent load)

Per-sampler SyncTimer: for each function, 1000 threads waited at the barrier simultaneously and fired together. Results:

CPU Profile (Wave)
  • Average: 9.6% (throughout test)
  • Peak: 74% (burst moment)
  • Result: Comfortably handled on 12 cores
RAM Profile (Wave)
  • Average: 54.4% (~17.7 GB)
  • Peak: 57% (~18.6 GB)
  • Delta: +2.6 pp — minimal memory pressure
Result: Under 1000 concurrent calls, Fast/Medium types maintain the same single-thread performance. Functions are stateless — no thread contention.
Question 3
Are there lazy-init spikes? (Does the first call show inflated latency?)

Yes, present in certain types. Most notable example: imei type avg=0.215 ms but p50=0.031 ms. The average is 7× the p50 — a sign that the first few calls include lazy-init latency (class loading, lookup table initialization) in the average.

Types with observed lazy-init spikes: imei (avg/p50 ratio 6.9×), color (avg/p50: 1.9×), slug (avg/p50: 1.4×). These types should go through setUp warmup.
Question 4
Does warmup help? (Does setUp warmup eliminate lazy-init spikes?)

Yes. AllTypes-Wave.jmx has a setUp Thread Group (1 thread, 1 loop) that calls all functions once in sequence. This completes JVM class loading and static init blocks before the test begins.

Without warmup (theoretical)
  • First call: class loading ~50–200 ms
  • Second call: normal latency
  • Noise introduced into p95 reports
After warmup (measured)
  • Fast type p50: 0.027–0.045 ms
  • p95 drift (76 min): +5.9% — stable
  • Spikes negligible
Evidence: p95 trend across Wave: first bucket 0.102 ms → last bucket 0.108 ms. p95 drift of +5.9% over 76 minutes — statistical stability proven.

METHOD Measurement Methodology — What Was Measured?

Measurement = System.nanoTime() delta ÷ 1000 → JTL Latency column, in microseconds. Only fn.execute() execution time is recorded. BeanShell parse (~2 ms) and SyncTimer wait are excluded.

CSV setUp + CSV Pre-Generation Script for Heavy Types

JSR223 Sampler · scriptLanguage: beanshell · setUp Thread Group · 1 thread · 1 loop  |  Note: Groovy does not work with JMeter 5.6.x + Java 25 (ASM / class file v69 incompatibility). BeanShell is required.

import com.mockjutsu.jmeter.functions.*;
import org.apache.jmeter.engine.util.CompoundVariable;
import java.io.*;

int N = 1000; String D = "C:/load-test-data/"; new File(D).mkdirs();

void w(fn, String t, String f) throws Exception {
    java.util.List p = new java.util.ArrayList();
    p.add(new CompoundVariable(t)); fn.setParameters(p);
    PrintWriter pw = new PrintWriter(new OutputStreamWriter(
        new FileOutputStream(D+f+".csv"),"UTF-8"));
    pw.println(f);
    for (int i=0;i<N;i++){
        String v=fn.execute(null,null);
        pw.println(v.contains(",")||v.contains("\n")
            ?"\""+v.replace("\"","\"\"")+"\"":v);
    }
    pw.close(); log.info("[mock-jutsu] "+f+".csv ("+N+" rows)");
}

MockJutsuOidcFunction   oidc = new MockJutsuOidcFunction();
MockJutsuAiFunction       ai = new MockJutsuAiFunction();

w(oidc, "oidc_token_set|TR", "oidc_token_set");
w(oidc, "jwks|TR",           "jwks");
w(ai,   "ai_embedding|TR",   "ai_embedding");
w(ai,   "ai_vector|TR",      "ai_vector");

SampleResult.setResponseData("4 types → "+N+" rows → "+D,"UTF-8");
SampleResult.setSuccessful(true);
CSV Data Set Config settings:
Filename: C:/load-test-data/oidc_token_set.csv  |  Variable Names: oidc_token_set  |  Sharing mode: All threads  |  Recycle: True
